# GameLink 下单页面开发文档（参考 delta-settlement）

版本：v1.1 ｜ 日期：2026-10-09 ｜ 状态：开发设计，页面与新增接口尚未实现

适用人员：产品、前端、后端、测试。本文依据已查看的 delta-settlement `main` 源码及本工作区 GameLink 源码编写。“已有接口”仅表示在本地源码中存在；“新增/扩展”均是开发要求，不代表已经验收或能够进行真实资金交易。

## 1. 页面定位与参考范围

下单页面定位为**客服后台录单工作台**：客服登记老板的陪玩订单，选择主副陪玩，录入原价、抽成、打赏、优惠，查看收益和押金预览，保存后进入收款核账与服务履约流程。页面入口放在现有管理后台“业务管理 → 订单管理”，路由沿用 `/admin/biz/order`，增加“录入订单”按钮。

参考项目：[Minnno7/delta-settlement](https://github.com/Minnno7/delta-settlement)。主要参考其订单记录、录入弹窗、按陪玩查看周期应结算的交互。客户自助选择时长和支付可作为后续独立页面，本文主流程面向客服录单。

## 2. 功能范围与交付阶段

完整目标包含普通单、双护单、体验单、外派单，端游/手游，老板预存关联，主副陪玩独立抽成，打赏、优惠、押金，周期汇总以及付款、退款、工资衔接。

| 阶段 | 交付内容 | 开放条件 |
|---|---|---|
| P1：普通单闭环 | delta 风格订单列表和录单表单；一名陪玩；老板、日期、平台、主题、备注；服务端抽成快照；人工收款核账；服务完成、T+7、工资追踪 | 录单、权限、核账、重复请求和退款验收通过 |
| P2：完整结算录单 | 双护/体验/外派、主副抽成、打赏、俱乐部承担优惠、独立押金账本、老板余额代扣、周期汇总 | 多人分账、优惠承担、押金并发、退款冲销验收通过 |
| P3：客户自助与支付渠道 | 客户选择游戏/陪玩/时长、真实钱包支付、第三方支付及回调 | 修复现有客户端模拟数据和创建订单问题，渠道独立验收 |

P1 不开放未接通的 P2 资金字段，不能保存后悄悄忽略。P2 必须按本文完整规则实现后才能标记“参考 delta 的完整录单功能已交付”。配置开关由服务端返回，后端也必须拒绝未开放功能。

## 4. 录单字段定义

金额输入显示元，API 和数据库统一使用整数分；比例显示百分数，API 使用整数基点（`1500` = 15%，`50` = 0.5%）。以下英文名称为拟定的新录单 DTO 字段，不是现有接口字段。

| 字段 | 必填/默认 | 规则及交互 |
|---|---|---|
| 老板 `customer_id` | 草稿可空；提交必填 | 搜索昵称、账号或手机号后选择真实客户 ID；显示余额。昵称仅作展示，不能作为扣款主键 |
| 业务日期 `business_date` | 必填，今天 | `YYYY-MM-DD`，按 Asia/Shanghai 归属周期；补录需要权限和原因 |
| 结算周期 `cycle_id` | 服务端匹配 | 展示周期名称和起止日；已封账周期禁止普通编辑 |
| 游戏 `game_id` | 提交必填 | 搜索已启用游戏；delta 的平台字段无法替代 GameLink 游戏 ID |
| 服务项目 `item_id` | 提交必填 | 必须与游戏和陪玩资格匹配，使用真实项目 |
| 平台 `platform` | 必填，端游 | `pc` / `mobile`，切换可更新未修改的默认抽成；用户已手动改比例时先提示 |
| 类型 `order_type` | 必填，普通单 | `normal` / `dual` / `trial` / `outbound` |
| 主陪玩 `primary_player_id` | 提交必填 | 仅可选有资格的有效陪玩；展示在职状态、押金目标和当前余额 |
| 副陪玩 `secondary_player_id` | 条件必填 | 双护单必须选择，体验/外派可选；不得与主陪相同；普通单隐藏并清空 |
| 主/副抽成 `club_rate_bps` | 默认规则 | 0～10000，建议50步长；快捷10%、15%；各自独立；修改需要权限和原因 |
| 原订单金额 `gross_amount_cents` | 提交必填 | 大于0、最多两位小数；P1为客服手工约定价格，后端检查金额上限和改价权限 |
| 老板打赏 `tip_cents` | 0 | 非负；全额分给陪玩，不抽俱乐部费用，不扣押金；必须有收款来源 |
| 优惠比例 | 0 | 标题写“优惠比例（减价%）”；输入10表示减10%，避免与“一折”混淆 |
| 优惠金额 `discount_cents` | 0 | 与比例双向联动，以最后修改字段为来源；0～原价；不减少陪玩原价计酬基数 |
| 主题玩法 `theme` | 可选 | 字典选项+自定义文本，最多100字；自定义内容不能直接修改共享字典 |
| 备注 `note` | 可选 | 最多500字，纯文本显示 |
| 收款方式 `collection_mode` | 暂不收款 | `uncollected` / `manual` / `wallet`；保存时不直接扣款 |
| 线下流水、实收时间、凭据 | 人工核账时必填 | 填真实渠道流水与凭据引用；由有核账权限的财务确认 |
| 实际服务开始/完成时间 | 履约/补录时填写 | 与业务日期分开；校验结束晚于开始，历史补录不得伪造已完成时间 |

优惠和抽成均需保存规则版本、修改原因及操作者。列表显示当时订单快照，后续改系统默认比例不能重算历史订单。

delta 允许老板昵称留空、不联动预存。GameLink 中保留“无老板草稿”即可；正式订单需关联客户，否则不能进入客户钱包或付款流程。匿名线下订单若后续确有需求，应另设非钱包账务模型，不能使用共用虚假客户账号。

## 5. 订单类型与动态联动

| 类型 | 参与人 | 原价与打赏分摊 | 普通陪玩俱乐部抽成 | 押金 |
|---|---|---|---|---|
| 普通单 | 一名 | 全额归该参与人计算 | 按快照比例 | 依押金缺口暂扣 |
| 双护单 | 两名，必须不同 | 各50% | 各用自身比例 | 各依自身缺口暂扣 |
| 体验单 | 一或两名 | 一名全额；两名各50% | 默认免抽成 | 依押金缺口暂扣 |
| 外派单 | 一或两名 | 一名全额；两名各50% | 默认免抽成 | 依押金缺口暂扣 |

“外派单”是订单类型；“外派陪玩”是陪玩属性。参考 delta，外派陪玩无论订单类型都按其抽成快照收费且免押金。GameLink 必须用明确的 `player_type=external` 或等价结构化字段判断，不能根据姓名包含“外派”判断。

delta 的计算函数对体验单即使没有副陪也按一半金额计算；本设计将其调整为**实际一人取全额、两人才平分**，避免漏计一半。该差异应写入测试。端游15%、手游10%、押金30%作为参考默认配置，不应散落在前端硬编码；规则须版本化并可由业务管理员配置。

切换类型为普通单时清空副陪与副陪比例，重新报价。免抽成时禁用普通陪玩的比例输入并标注“本类型免抽成”；外派陪玩显示其有效比例和“免押金”。选择陪玩后拉取其规则，不能通过前端传递免押金标志绕过后端校验。

## 6. 金额计算与资金守恒

### 6.1 计算顺序

设原订单金额为 `G`，优惠为 `D`，打赏为 `T`，单位均为分。老板应付 `P = G - D + T`。统一将打赏纳入本单收款；参考 delta 的预存预览只减原价优惠，本设计补齐打赏，避免预存漏扣。

先按实际人数分配原价 `g_i` 和打赏 `t_i`，再按各参与人规则计算：

```text
俱乐部抽成 c_i = roundHalfUp(g_i × 有效抽成基点 / 10000)
抽成后服务收益 a_i = g_i - c_i
押金缺口 r_i = max(0, 押金目标 - 正式入账时押金余额)
押金暂扣 d_i = min(roundHalfUp(a_i × 押金基点 / 10000), r_i)
服务净收益 e_i = a_i - d_i
本单应结算 s_i = e_i + t_i

俱乐部毛抽成 C = Σc_i
俱乐部承担优惠 = D
俱乐部净额 = C - D
老板应付 P = (C - D) + Σd_i + Σs_i
```

优惠全额由俱乐部承担，陪玩按原价计酬。优惠超过毛抽成时会产生负俱乐部净额，必须明确展示；默认拒绝提交，只有配置了补贴预算且具有超额优惠权限时才能提交并记补贴支出。不得把亏损转为未经说明的陪玩扣款。

输入金额通过十进制字符串解析到整数分，禁止用浮点数直接做财务运算。正数比例计算采用四舍五入；两人分摊时主陪取整除的一半，余分归副陪，并在明细中展示，保证合计等于原金额。冲销直接取原分录的相反数，不重新舍入。

P2 首期仍只支持一张订单的一次足额付款，不提供分次付款或组合付款。100%优惠且无打赏时应付为0，不伪造0元付款记录；必须走有补贴审批的“免付款已批准”路径，服务完成校验该批准记录。该路径尚未实现前，阻止零应付订单提交。

### 6.2 计算验收示例

| 场景 | 条件 | 预期结果（元） |
|---|---|---|
| 普通单含优惠和打赏 | 原价100，抽成15%，押金30%，缺口足够，打赏20，优惠10 | 老板付110；抽成15；押金25.50；服务净收益59.50；陪玩应结算79.50；俱乐部净额5 |
| 押金接近目标 | 原价100，抽成15%，押金只差5 | 押金只扣5；服务净收益80；老板付100；抽成15；陪玩80 |
| 双护单独立比例 | 原价100，主15%/副10%，均押金30%，打赏20，优惠10 | 主抽成7.50/押金12.75/应结算39.75；副抽成5/押金13.50/应结算41.50；老板付110；俱乐部净额2.50 |
| 单人体验 | 原价100，普通陪玩，押金缺口足够 | 抽成0；押金30；陪玩70；原价完整计入 |
| 外派陪玩 | 原价100，体验单，外派陪玩抽成15% | 抽成15；押金0；陪玩85 |
| 双护出现余分 | 原价100.01，其他费率为0 | 主50；副50.01；合计100.01 |

打赏属于陪玩收益，不计俱乐部抽成或押金基数。独立扣款、转单代付、违约金放在调整单中，并需审批及凭据；录单页面不混入这些调账操作。周期预计应结算可以汇总 `订单净收益+打赏+已批准调整`，但真正可发工资必须另取已解冻且未被预留的余额。

## 7. 收款、履约与工资状态

禁止一个“已结算”字段同时代表已收款、已服务和已发工资。页面展示以下独立状态，取值为建议的新聚合展示模型。

| 状态维度 | 展示状态 | 触发依据 |
|---|---|---|
| 录单 | 草稿 / 已提交 / 已作废 | 保存、提交或作废命令 |
| 付款 | 未收款 / 待核账 / 已核账 / 退款中 / 已退款 / 免付款已批准 | Payment、真实流水或补贴批准记录 |
| 服务 | 待确认 / 已确认 / 服务中 / 已完成 / 已取消 / 争议中 | 复用现有 Order 生命周期 |
| 工资 | 未入账 / 冻结中 / 可结算 / 已预留 / 已发放 / 已冲销 | 分账、钱包、提现与发放流水；部分发放另显示金额 |

流程：保存草稿 → 提交录单 → 登记收款或授权余额代扣 → 财务核账 → 确认/开始/完成服务 → 分账入冻结收益及押金账本 → 按现有 T+7 规则解冻 → 工资准备/发放登记。服务完成必须检查有效足额收款或免付款批准；所有资金步骤均由后端执行。

保存草稿和提交录单均不增加陪玩钱包余额、不生成押金暂扣，也不直接扣老板余额。实时预览为预计值；服务完成正式入账时锁定押金账户并读取实际缺口，冻结实际分账快照，后续报表不能重算并再次入账。

实际完成时间决定 T+7，不能用业务录单日期代替。历史补录应由专门权限登记完成证据，经审批后按规则处理；封账后的补录及更正通过当前开放周期的调整单，保留原业务日期和原周期引用。

### 7.1 老板预存与人工核账

“老板预存”复用真实客户钱包可用余额。客服代扣须有单独的代操作权限与授权记录，扣款前显示老板、订单号、总应付、扣前及扣后余额，执行独立扣款命令。后端从订单读取客户ID和应付金额，在事务中校验余额并扣减一次，写支付与钱包流水。前端无权直接改余额。

人工收款先创建待核账 Payment，再由财务核实真实渠道流水、金额、币种、支付时间和凭据。截图或客服勾选不能自行变为已付款；真实流水全局防重复。微信/支付宝自动支付尚未接通，页面不展示可自动完成支付的按钮。

### 7.2 作废、退款与更正

无财务分录的草稿可删除；已提交订单采用作废并保留审计；已核实收款必须通过退款流程，不能直接改成“退款作废”。已产生工资分账时先冻结相关可发放额度，再按原规则快照冲销分账、押金及优惠承担，最后完成退款。

首期全额退款：退款上限为客户实际付款 `P`，冲销原订单全部相关分录，不能按原价 `G` 超额退钱。已发工资、押金已退还或余额不足以冲回的订单，进入财务异常处理并保留追偿/调整记录，不自动制造负余额或宣称已退款成功。外部退款需真实退款流水；钱包退款只回真实客户钱包。

delta 完整规则上线前，需要重新验收现有退款服务对多人、打赏、优惠、押金的支持。部分退款在完成各项分摊和冲销策略前关闭入口。财务字段入账后锁定，改陪玩、金额、抽成均通过撤销重录或调整单完成，禁止直接覆盖历史分录。

## 8. 结算周期与列表汇总

周期采用不重叠的半开日期区间 `[start_date, end_date)`，按上海业务日期匹配，边界日只属于一个周期。没有有效周期时拒绝提交并给出建周期入口。已经存在重叠周期的数据必须迁移修正，不能临时让客服随机选择。

列表汇总分三种口径：订单原价/优惠/应付按业务订单计算；抽成/押金/应结算按正式分账快照计算；收款/退款/已发工资按实际流水计算。未入账订单显示“预计”，不混入已入账余额。

选中陪玩后显示“本周期订单应结算”“当前冻结”“本周期已发放”和“当前可发放余额”。最后一项是该陪玩全账户当前余额口径，须标注“账户余额，含其他周期”；不能把周期金额直接当成可提现余额，也不能把一次混合多周期发薪全部算在本周期。

周期封账须校验待核账、争议、未完成订单，并记录例外审批；封账只生成报表快照，不触发钱包再次入账。发放跨周期工资时保存对应分账分配明细，报表才能正确追溯每个周期的已发金额。

## 9. GameLink 现有接口与改造点

下文代码位置均相对于 GameLink 仓库根目录。以下 API 都以 `/api/v1` 为前缀。

| 已有 API | 当前用途 | 本方案处理 |
|---|---|---|
| `POST /admin/orders` | 创建基础订单 | 保留兼容；新增录单服务补齐快照、草稿和参与人模型 |
| `GET /admin/orders`、`GET /admin/orders/:id` | 列表、详情 | 扩展平台、类型、周期、客户、参与陪玩和分账状态查询 |
| `POST /admin/orders/:id/confirm`、`/start`、`/complete` | 履约状态命令 | 完成服务扩展为多人原子分账，同时保留收款真实性校验 |
| `POST /admin/payments` | 创建待核账付款记录 | P1复用；P2金额依据客户应付；扩展请求幂等 |
| `POST /admin/payments/:id/capture` | 人工收款核账 | 复用真实流水验证，扩展打赏/优惠收款组成 |
| `GET /admin/orders/:id/payments` | 查付款记录 | 详情展示实收、退款、凭据及核账人 |
| `POST /admin/orders/:id/refund` | 退款/外部退款登记 | 多人、押金、优惠冲销完成前不得开放复杂订单退款 |

现有基础订单创建字段包括 `user_id`、`player_id`、`game_id`、`item_id`、`title`、`description`、`total_price_cents`、`currency`、`scheduled_start/end`，没有 delta 完整录单字段。当前人工核账请求有 `provider_trade_no`、`provider_raw`、`paid_at`。新增字段不能塞入备注后当作可检索财务数据使用。

必须改造的后端能力：

1. 现有 `CommissionRecord` 按订单唯一且绑定一个陪玩，改为订单参与人分账；旧订单保持原规则，历史记录不重算。
2. 当前完成服务对多人订单有拒绝保护，且收款与订单金额等额匹配。新增规则明确 `gross=原价`、`payable=应付`，兼容旧 `TotalPriceCents` 为应付的语义；计酬改读原价快照，收款读应付，不能为了优惠而删除校验。
3. 当前佣金需增加录单抽成快照和规则版本；正式入账复用录单锁定规则，避免保存后仍按另一个默认佣金结算。
4. 新建押金负债账本。现有 `FrozenCents` 为T+7收益、`WithdrawFrozenCents` 为提现预留，均不能充当押金。
5. 新增打赏、优惠承担和补贴分录；系统需能审计“老板少付但陪玩按原价拿钱”的差额资金来源。
6. 订单保存、代扣、核账、完成、退款、解冻和工资发放各有独立幂等约束及审计；不能靠禁用按钮保证不重复入账。

## 10. 新增接口建议与示例

以下为**建议新增合同**，路径与 DTO 应在开发时落地至 OpenAPI。后端统一 snake_case，请求和响应采用项目原有 API 信封；前端通过适配器转换，禁止混用旧字段。

| 新增 API | 功能 | 关键约束 |
|---|---|---|
| `GET /admin/order-entry/options` | 可用功能、类型、比例、开放周期、限额 | 从认证主体计算可操作能力 |
| `POST /admin/order-entry/quote` | 实时预览主副分账、应付、押金缺口 | 不动资金；返回规则版本、报价ID、有效期 |
| `POST /admin/order-entries` | 保存草稿或提交 | 幂等键必填，重新校验客户、陪玩、周期、权限、报价 |
| `PUT /admin/order-entries/:id` | 编辑未入账录单 | 乐观锁 `expected_version`，已收款财务字段禁止直接编辑 |
| `POST /admin/order-entries/:id/submit` | 草稿正式提交 | 建立真实订单，重复提交返回同一订单 |
| `POST /admin/order-entries/:id/void` | 无资金订单作废 | 需要原因；已收款提示退款路径 |
| `POST /admin/orders/:id/collect-wallet` | 客服授权代扣预存 | 独立权限、授权引用、事务余额校验、唯一扣款流水 |
| `GET /admin/orders/:id/allocations` | 正式分账明细 | 区分预览与已入账快照 |
| `GET /admin/settlement-cycles/:id/order-summary` | 周期订单及参与人汇总 | 与列表条件、分页和导出使用同一口径 |

草稿保存只要求基础结构合法，可以缺少客户或项目；正式提交严格校验完整字段。客户端发 `action=submit` 时，后端在同一事务保存录单、建立基础订单和分账计划；正式分账及押金流水在服务完成时生成。

完整版本的报价/录单输入示例（示例 ID 无真实含义）：

```json
{
  "action": "submit",
  "customer_id": 101,
  "business_date": "2026-10-09",
  "cycle_id": 12,
  "game_id": 3,
  "item_id": 8,
  "platform": "pc",
  "order_type": "dual",
  "participants": [
    { "player_id": 201, "role": "primary", "club_rate_bps": 1500 },
    { "player_id": 202, "role": "secondary", "club_rate_bps": 1000 }
  ],
  "gross_amount_cents": 10000,
  "tip_cents": 2000,
  "discount_cents": 1000,
  "discount_reason": "活动优惠",
  "theme": "三角洲护航",
  "note": "老板希望语音沟通",
  "collection_mode": "manual",
  "quote_id": "q_example",
  "rule_version": "delta-v1"
}
```

保存请求额外带 `Idempotency-Key` 头，报价请求不需要 `action`。禁止客户端提交 `is_outsource`、押金余额、最终收益或已付款状态；这些由服务端查询并计算。

报价返回 API 信封中 `data` 的示例：

```json
{
  "quote_id": "q_example",
  "rule_version": "delta-v1",
  "expires_at": "2026-10-09T12:05:00+08:00",
  "gross_amount_cents": 10000,
  "tip_cents": 2000,
  "discount_cents": 1000,
  "payable_cents": 11000,
  "club_commission_cents": 1250,
  "club_net_cents": 250,
  "estimated_deposit_cents": 2625,
  "estimated_settlement_cents": 8125,
  "allocations": [
    { "player_id": 201, "gross_share_cents": 5000, "club_cents": 750, "deposit_cents": 1275, "earning_cents": 2975, "tip_cents": 1000, "settlement_cents": 3975 },
    { "player_id": 202, "gross_share_cents": 5000, "club_cents": 500, "deposit_cents": 1350, "earning_cents": 3150, "tip_cents": 1000, "settlement_cents": 4150 }
  ],
  "deposit_is_estimate": true
}
```

报价有效期建议5分钟。输入修改后200～400ms防抖请求，取消或忽略旧请求响应；只有最新成功报价且无校验错误才能提交。保存时规则或报价不匹配返回409并要求刷新预览；押金预览过时不自动扣款，实际服务完成时重新锁定缺口并记录最终明细。

同一幂等键、同一请求返回同一业务结果；同一键、不同载荷返回409。幂等作用域包含操作者、操作类型和键，持久化请求哈希及结果，事务回滚不得留下成功标记。网络超时保留原键重试或查询结果，不能立即生成新键重复保存/扣款。

错误合同：400字段/金额错误，401未登录，403无权限，404实体不存在，409版本/状态/幂等冲突，422余额不足或规则不满足，503未接通支付渠道。错误响应携带业务码和可定位的字段；所有状态最终由后端校验。

## 11. 数据模型、迁移和事务

| 模型（建议） | 关键数据 |
|---|---|
| `OrderEntry` | 草稿/提交状态、业务日期、周期、业务订单ID、版本、录单者 |
| `OrderFinancialSnapshot` | 原价、优惠、打赏、应付、规则版本、收款方式、快照时间 |
| `OrderParticipant` | 订单、陪玩、主副角色、分摊比例、陪玩类型、抽成/押金规则快照 |
| `OrderAllocation` | 原价分摊、抽成、押金、服务净收益、打赏、应结算、解冻时间及入账状态 |
| `DepositAccount/DepositFlow` | 陪玩、押金目标、余额、缴纳/暂扣/冲销/扣罚/退还、业务唯一键 |
| `SettlementCycle` | 不重叠日期区间、开放/封账、版本、封账审计 |
| 财务分录和审计 | 收款清算、俱乐部抽成、优惠承担、陪玩应付、押金负债、退款、操作者与证据 |

资金入账时在一个数据库事务中锁订单、参与人钱包和押金账户，按固定顺序锁参与人ID防止死锁；验证收款、读取押金余额、创建唯一分账与流水、更新余额、写审计。任何一步失败全部回滚。并发完成两张订单不能超扣同一陪玩的押金目标。

唯一约束至少包含：订单参与人 `(order_id, player_id)`、分账业务键、押金流水业务键、钱包业务键、渠道真实流水、请求幂等键。用户与陪玩的对应关系由后端加载，不接受前端指定收款钱包归属。

旧订单迁移为单参与人，原价=原应付、优惠/打赏/押金=0，并保存历史规则标识；旧已入账记录以实际金额导入，不按新比例重算。新旧记录都须能在工资汇总和退款追溯中识别。上线前做迁移备份、合计对账与回滚演练。

## 12. 权限、操作反馈与审计

拟定权限包括录单查看/创建/编辑/提交、价格及抽成调整、超额优惠、老板余额代扣、人工核账、历史补录、退款、周期封账、工资准备和发放。与现有“HTTP方法+路径”权限体系绑定，前端隐藏按钮仅是体验控制。

录单客服默认可创建/提交，人工核账和真实发放由财务权限控制；高风险代扣、超额优惠和历史补录另授权。审计保存订单号、操作者、操作时间、前后财务快照、原因、请求ID及凭据引用。凭据接口需权限校验，日志不得记录密码、令牌或完整敏感账户数据。

交互要求：选择框远程搜索并分页；加载、空状态、失败和重试均可见；提交期间禁止重复点击；关闭有改动的表单提示是否丢弃；服务器拒绝时保留输入；保存成功返回订单号和“待收款/待核账”等真实下一状态。未收款不能提示“工资已结算”。

## 14. 验收清单与完成标准

| 范围 | 必须验证的场景 | 通过标准 |
|---|---|---|
| 页面联动 | 普通→双护→普通；切换平台、主副陪、优惠比例与金额 | 隐藏字段被清空，报价跟随最新输入，副陪不能重复 |
| 核心计算 | 第6节全部示例、金额1分、100%抽成、押金缺口0/1分 | 整数分结果正确，守恒差额为0，无负应结算 |
| 规则快照 | 保存后修改默认比例、陪玩类型或押金规则 | 历史抽成按快照，押金实际缺口按入账时账户余额 |
| 人工收款 | 无流水、重复流水、金额不符、伪造已付款状态 | 拒绝核账；有效付款才可进入正式完成入账 |
| 预存代扣 | 余额不足、两次并发、超时重试、无代扣权限 | 不超扣，不重复扣，失败无部分资金写入 |
| 多人入账 | 同单重复完成、两单并发补押金 | 一个老板付款；每参与人一次入账；押金不超目标 |
| 优惠与打赏 | 打赏进入应付，优惠不减陪玩计酬，优惠超毛抽成 | 补贴可追溯；无权限或预算时拒绝；各金额分录匹配 |
| 退款与更正 | 全额退款、重复退款、已经发薪、已退押金 | 按实际付款退款；原分录准确冲销；异常转人工处理 |
| 周期 | 起止边界、重叠周期、封账后补录、多人筛选 | 归属唯一；禁止改封账历史；总金额不因副陪翻倍 |
| 工资 | 完成后冻结、T+7解冻、准备工资、重复发放登记 | 可发放余额准确；预留不混入可用；真实发放有证据 |
| 权限与审计 | 越权直接调用接口、财务记录删除、敏感日志 | 后端拒绝；原财务流水保留；所有资金操作可追溯 |
| 故障恢复 | 事务中任一步失败、数据库冲突、网络超时 | 全部回滚或返回同一已提交结果，无孤立流水 |

验证采用后端表驱动财务测试、真实数据库事务/并发集成测试、前端字段联动与报价竞态测试，以及客服录单→财务核账→服务完成→解冻→工资登记的端到端流程。外部支付使用沙箱或测试凭据；真实资金验收另行组织。

交付时提交界面截图、API合同、迁移及回滚步骤、测试结果、对账报表样例。新增路径须完成权限种子注册；前后端构建和相关检查通过。项目原有构建错误若仍存在，应单独列明，不能把部分测试通过写成整项目验收通过。

**完成标准：** 客服能按 delta 的录单习惯登记订单，老板应付、陪玩应结算、俱乐部抽成及优惠承担、押金暂扣均可核对；资金流只由真实收款和后端事务产生；保存订单、完成服务、工资发放在页面及报表中都有清晰、可审计的独立状态。
